## Разбор предыдущего результата

- **Подтверждённые недостатки.** В админке были видны попытки, но отсутствовал список засчитанных решений (§2). `check_stack.py` мог объединить успешные ответы одного экземпляра с Docker-проверками другого. Отчёт о ресурсах мог пройти с одной строкой вывода. Отрицательное соединение с app считалось доказательством даже без подтверждения, что app доступен из собственной сети. `compose_e2e.py` допускал запуск с отключёнными Python-утверждениями.
- **Обязательные проверки.** Прохождение WEB-01 от скрытой страницы до начисления баллов (§4 и критерий завершения) остаётся открытым. Приём синтетического ответа подтверждает форму и рейтинг. Чистый том проверен на данном ноутбуке через отдельный порт. Чистый ноутбук с портом 8080 и защита на нём ещё не проверены (§10, §12). Результаты меньших проверок приведены ниже.
- **Ограничения и дополнительные испытания.** В §5 сказано CRUD, а в сценарии §2 описано скрытие. Физическое удаление задания отсутствует. Для удаления карточки с результатами требуется договориться о влиянии на историю и рейтинг. Отдельные активные проверки SQL-инъекций и XSS в §10 не перечислены. VM, командный рейтинг, CSV, CI, PostgreSQL, подсказки и второй контейнер перечислены как дополнительные (§13). Изменение рабочего стека отложено по условиям задачи.

## Сценарий защиты

1. На подготовленном ноутбуке запустить Compose одной командой, открыть главную и каталог, показать три healthy-сервиса и схему сетей из README.
2. Через отдельные профили браузера зарегистрировать двух участников. Показать неверный ответ, принятую сдачу, отсутствие повторного начисления и правило равных баллов. Подключить ещё 3–8 участников для мини-турнира. Для закрытия готовности нужны результаты полного прохождения всех трёх заданий, включая WEB-01.
3. Войти как преподаватель, сменить начальный пароль, опубликовать и скрыть тестовую карточку, показать попытки, решения и рейтинг.
4. На демонстрационном проекте показать сохранность после restart, HTTP 503 при остановке лаборатории, рабочий каталог и рейтинг, замер CPU/RAM и повторный запуск из заранее собранных образов без внешнего маршрута.

## Безопасный перенос на рабочий адрес

Перенос возможен после закрытия открытых обязательных испытаний и отдельного разрешения на обновление рабочего сервиса.

1. Зафиксировать проверенный локальный коммит и сохранить прежние исходники и образы. Через `docker compose ls` и `docker compose ps` подтвердить имя старого проекта, путь к его Compose-файлу и фактический том SQLite. Рабочие данные остаются в исходном томе.
2. Получить согласованный SQLite-снимок через SQLite Online Backup API. Для версии с `app/backup.py` использовать команды из [README](../README.md#резервное-копирование-и-восстановление). Если файла в старом образе нет, выполнить `sqlite3.Connection.backup()` внутри контейнера app из `/data/cyberarena.db` в новый приватный файл, затем перенести его через `docker compose cp`. Сохранить прежний ключ подписи и манифест флагов, если он уже есть, в закрытом хранилище. Проверить `PRAGMA integrity_check` и `PRAGMA foreign_key_check` на снимке.
3. Восстановить копию в пустой том отдельного проекта на свободном loopback-порту по инструкции README. Для старой схемы без манифеста проверить сопоставление встроенных карточек, при необходимости задать новую `FLAG_REVISION` и сохранить прежний `SECRET_KEY`. Сверить число пользователей, карточек, попыток и решений, рейтинг, вход и локальные ресурсы. Убедиться, что восстановление реально поднимает приложение.
4. На согласованном окне остановить только старый Nginx командой `docker compose -p <старый-проект> -f <старый-compose> stop nginx`. Дождаться завершения принятых запросов. Снять свежий согласованный снимок, проверить его и повторить восстановление в **новом** пустом томе проекта `cyberarena-cutover`. Зафиксировать ожидаемые счётчики перед запуском.
5. После восстановления запустить подготовленные образы командой `CYBERARENA_PORT=8080 docker compose --env-file <закрытый-env> -p cyberarena-cutover up -d --no-build --pull never --wait`. Образы с тегами проекта `cyberarena-cutover` должны быть собраны заранее. Перед открытием турнира проверить три healthcheck, вход, данные, ресурсы и изоляцию чтением. Сохранить прежний стек и его том для отката.
6. При сбое до приёма новых записей остановить Nginx проекта `cyberarena-cutover` и запустить старый Nginx через `docker compose -p <старый-проект> -f <старый-compose> start nginx`. Проверить `/health` и рейтинг. Если после переключения уже появились записи, сохранить новый SQLite-снимок и согласовать их перенос до возврата трафика.
